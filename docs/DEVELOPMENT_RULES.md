# Development Rules — 开发规范

> 所有开发者（包括 AI 和人类）必须遵守。

---

## 1. 开发流程

```
模块选择
    ↓
  .h 设计
    ↓
 GPT Review ──→ 通过 ──→ .cpp 实现
    ↓                        ↓
  修改                    GPT Review ──→ 通过 ──→ Integration Test
                            ↓                        ↓
                          修改                    GPT Review ──→ 通过 ──→ Next Module
                                                    ↓
                                                  修改
```

### 说明

| 阶段 | 内容 | 通过标准 |
|------|------|----------|
| `.h` 设计 | 接口定义、类结构、注释、依赖关系 | 接口清晰、无冗余依赖、注释完整 |
| **Review** | GPT 审核头文件 | 接口可被调用方正确理解和使用 |
| `.cpp` 实现 | 功能实现、错误处理、日志输出 | 逻辑正确、边界条件处理、日志合适 |
| **Review** | GPT 审核实现 | 无内存泄漏、无未定义行为、符合架构 |
| **Integration Test** | 真实硬件编译、烧录、验证 | 串口输出符合预期、UI 正常、无 crash |
| **Review** | GPT 审核测试结果 | 功能正确、性能可接受、无回归 |

---

## 2. 接口冻结规则

1. `.h` 审核通过后**默认冻结**，禁止随意修改。
2. 已冻结接口列表见 [INTERFACE.md](INTERFACE.md)。
3. 只有以下情况允许修改已冻结接口：
   - **Bug**：接口行为与文档描述不符
   - **阻塞后续开发**：接口不足以支持新模块的功能需求
   - **严重性能问题**：接口设计导致无法接受的性能损耗
4. 修改已冻结接口需要：
   - 更新 [INTERFACE.md](INTERFACE.md)
   - 更新 [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md)
   - 更新受影响的所有 .cpp 实现
   - 通过 Integration Test

---

## 3. 架构冻结规则

已经审核通过的架构设计，**禁止为了"更优雅"进行重构**。

只有以下情况允许修改架构：

- **Bug**：架构设计导致正确性问题
- **影响后续开发**：当前架构不足以支持后续模块
- **严重性能问题**：架构导致不可接受的性能损耗

禁止的修改类型：
- "优化"命名
- "统一"代码风格
- 引入设计模式（除非解决上述三类问题）
- 拆分/合并模块（除非解决上述三类问题）

---

## 4. Code Review 规则

### GPT 审核范围（必须检查）

| 检查项 | 说明 |
|------|------|
| Bug | 逻辑错误、边界条件、未定义行为 |
| 生命周期 | 内存泄漏、野指针、悬空引用 |
| 空指针 | 未检查 nullptr 就解引用 |
| 资源释放 | malloc/free、new/delete 配对 |
| 架构一致性 | 是否符合 [ARCHITECTURE.md](ARCHITECTURE.md) |
| 接口一致性 | 是否符合 [INTERFACE.md](INTERFACE.md) 中已冻结的接口 |

### GPT 审核禁止范围

| 禁止项 | 说明 |
|------|------|
| 代码风格建议 | 命名、缩进、空格 |
| 命名建议 | 变量/函数/类重命名 |
| 无意义优化 | 在不必要时优化性能 |
| 个人偏好 | 任何主观偏好 |

---

## 5. 禁止跨模块修改

开发某模块时，**禁止顺手修改其他模块**。

例外：GPT 开发指令明确要求修改多个模块。

---

## 6. 禁止提前开发

当前模块未完成（未通过全部 Review + Integration Test）之前，**禁止开发下一模块**。

---

## 7. README 更新规则

每完成一个模块，更新 [README.md](../README.md) 中的：

- **Current Module** — 更新为刚完成的模块名
- **Next Module** — 更新为下一模块名
- **Current Stage** — 如有阶段性变化则更新
- **Version** — 更新版本号

---

## 8. 开发优先级

```
稳定 > 正确 > 可维护 > 性能 > 代码风格
```

1. **稳定**：系统不崩溃、不重启、不卡死
2. **正确**：功能行为符合预期
3. **可维护**：代码清晰、文档完整、遵循规范
4. **性能**：响应时间、帧率、内存占用
5. **代码风格**：命名、格式、注释风格

---

## 9. 职责划分

### Tech Lead（GPT）

- 架构设计
- 开发路线规划
- Code Review（`.h` / `.cpp` / Integration Test 各阶段）
- 项目管理（ROADMAP / DEVELOPMENT_LOG / INTERFACE）
- 回答开发者的技术问题

### Claude Code

- 按照开发指令生成代码
- 生成 `.h` 和 `.cpp` 文件
- 遵循项目架构和接口规范
- 响应 Review 意见并修改代码

### Developer（人类）

- 编译代码（`pio run`）
- 烧录固件（`pio run --target upload`）
- 运行测试（`pio device monitor`）
- 反馈测试结果（串口日志、UI 截图、异常描述）
- 做出最终决策（B 类建议的采纳/拒绝）

---

## 10. 建议分类规则

### A 类建议（必须执行）

影响以下方面的建议，**默认直接纳入开发流程**：

- 架构设计
- 接口定义
- 开发规范
- 可维护性（可能引发未来 Bug 的问题）

### B 类建议（可选）

以下方面的建议，**由 Developer 自行决定是否采用**：

- 代码风格（命名、格式）
- 性能优化（非瓶颈点）
- 工具优化（IDE 配置、脚本）
- 额外文档

### 分类流程

```
GPT 提出建议
    ↓
Tech Lead 分类
    ↓
┌── A 类 → 纳入开发流程 → Developer 执行
└── B 类 → Developer 决定 → 采纳 / 记录 / 拒绝
```

## 11. 通用编码规范

| 规范 | 说明 |
|------|------|
| **头文件保护** | `#pragma once` |
| **前置声明** | `.h` 中不引入重量级库头文件（lvgl.h / ESP_Panel.h），使用前置声明 |
| **注释** | 所有 public 方法使用 `/// @brief` Doxygen 风格 |
| **日志** | 使用 `Logger::info/warn/error` |
| **日志频率** | `update()` 中不输出高频周期日志 |
| **安全** | WiFi 密码、API Key 不硬编码、不输出日志 |
| **错误处理** | `begin()` 返回 bool，失败时 `Logger::error` 报告原因 |
| **命名** | 类名 PascalCase / 方法名 camelCase / 成员变量 `trailing_` |
